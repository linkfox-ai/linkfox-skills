# 工作流关联：registerWorkflow / listWorkflows / updateWorkflowTriggerTable / unregisterWorkflow

本文件覆盖四个操作，管的是「一条工作流（自动化）挂在哪个多维表下、由哪张数据表触发」这层**关联关系**；流本身的定义、节点、启停都在工作流侧，这里不建、不删、也碰不到。
调用方通常是工作流侧，或帮用户搭自动化的 agent：用户说「做个自动化」「监听这张表」时，流先在工作流侧建好，再来这里登记。
四者是一条生命周期：工作流侧建流 → `registerWorkflow` 登记 → `listWorkflows` 查看 / 排查 → `updateWorkflowTriggerTable` 换表或解绑 → 要删流时先 `unregisterWorkflow` 解除、再到工作流侧删流。
三个 id 的关系：`flowId` 是工作流侧那条流的 id，`notebookId`（`nbk` 开头）是它挂靠的多维表（容器），`tableId`（`tbl` 开头）是那个多维表里驱动它的数据表；一条流只属于一个多维表、最多绑一张触发表，且触发表必须在它所属的多维表里面。

## 四个操作共用的概念

### 三个 id 从哪来

| id | 是什么 | 从哪取 | 别这样做 |
|---|---|---|---|
| `flowId` | 工作流侧那条流的 id | 工作流侧给；已登记的可用 `listWorkflows` 查 | **不要自己编**。格式归工作流侧定，脚本只查非空、不查前缀 |
| `notebookId` | 多维表（容器）id，`nbk` 开头 | `listMyTables` / `listSharedTables`（见 `references/tables.md`）出参**顶层**的 `notebooks[].notebookId` | **别拿 `tableId` 顶替**——两个列表接口的出参是两层的，这是最常见的错法 |
| `tableId` | 数据表 id，`tbl` 开头 | `listMyTables` 里**同一个多维表**下的 `notebooks[].tables[].tableId` | 别从别处拿一个 `tableId` 直接试：不在流所属的多维表里就是 400 |

### 两层关联，别混

| 层 | 字段 | 含义 | 能不能空 | 表被删除 / 移出多维表时 |
|---|---|---|---|---|
| 归属 | `notebookId` | 这条流挂在哪个多维表下——决定它出现在哪棵侧栏树里、按谁的权限判 | **必填** | **不变** |
| 触发 | `tableId` | 由哪张数据表的记录变化来驱动它 | **可空** | **自动置空**，关联留着 |

- **`tableId` 为 `null` 的流不会被任何记录变化触发**，但照样出现在侧栏和 `listWorkflows` 里、看着很正常——排查「自动化怎么不跑」最该先看这一项。
- 自动置空**不需要调用方做任何事**：删表、删节点、把表移出容器三个入口后端都挂了清理，那条流退回「没有触发表」。所以原触发表被删时**不用**调 `updateWorkflowTriggerTable`。
- ⚠️ 已知缺口：这次自动置空目前**无法通知工作流侧**，他们画布上可能还显示那张已删的表——用户看着是配好的，实际不触发。等对方提供接收端后补上。
- `updateWorkflowTriggerTable` 只改触发层，不动归属（流仍挂在原来那个多维表下）。

### 四个操作都适用的规则

- **不收 `baseId`**：范围由调用方所在团队自动推导（一团队一 base），所以跨不出自己团队、也不可能登记到别的团队去。
- **出参里没有流的名字**，只有 `flowId`。名字、启停状态、触发条件、节点定义都在工作流侧，多维表这边一概不存——存一份副本就会与真相漂移（上游按钮字段那份 `isActive` 快照就是这么坏掉的）。要名字拿 `flowId` 去工作流侧查；**不要自己编名字，也不要把 `flowId` 说成流的名称**。
- **`flowId` 不校验格式**（由工作流侧生成），所以传错**不会当场报错**：`registerWorkflow` 会登记出一条指向不存在的流的关联，`updateWorkflowTriggerTable` / `unregisterWorkflow` 只会回 `status: "not_found"`。
- **一条流只能绑一张触发表**，`tableId` 是单值不是数组。
- **触发表只能选流所属多维表里的表**，否则 400。这是**权限校验**不是格式校验：推送出去的是**整行数据快照**，允许跨多维表绑定等于把一张调用方无权访问的表的数据送给那条流。
- **判权口径各不相同（刻意的）**：`registerWorkflow` / `updateWorkflowTriggerTable` 要求当前身份对那个多维表是**拥有者 / 创建者 / 可编辑者**之一，只读成员做不了；`listWorkflows` 按可见性过滤；`unregisterWorkflow` **不判容器写权限**、只守团队边界（理由见该节）。
- 响应数据**顶层平铺**，没有 `data` 这一层。
- `errcode: 401` = 身份未确立：网关未注入身份头，或该成员在用户中心查不到。500 的 `errmsg` 已消毒；500 / 503 能不能直接重试**各操作不同**，见各节「常见错误」。

## registerWorkflow —— 把一条已存在的流登记到某个多维表下面

**何时用 / 不该用**：
- 用：工作流侧刚建好一条流，要把它挂到某个多维表下；登记失败 / 超时后重试（幂等，安全）。
- 不该用：要**创建**工作流 → 本操作不做，到工作流侧建；只想**改触发表** → `updateWorkflowTriggerTable`；要**解除**关联 → `unregisterWorkflow`；要**看**已有哪些关联 → `listWorkflows`；要建多维表或数据表 → `createTable` / `addTable`（见 `references/tables.md`）。

**调用**：`python scripts/smart_table.py registerWorkflow '{"notebookId":"nbkXXXXXXXX","flowId":"your-flow-id"}'`

### 参数
| 参数 | 类型 | 必填 | 默认 | 约束 | 说明 |
|---|---|---|---|---|---|
| notebookId | string | **是** | — | `nbk` 开头 | 多维表（容器）id，取 `listMyTables` / `listSharedTables` **顶层** `notebooks[].notebookId` |
| flowId | string | **是** | — | 非空字符串，**不校验格式** | 工作流侧那条流的 id，从工作流侧拿，不要自己编 |
| tableId | string \| null | 否 | `null` | `tbl` 开头，或 `null`；**必须在 `notebookId` 这个多维表下** | 触发表。不传 / `null` = 触发器还没配完，这条流不会被任何记录变化触发 |

### 响应
| 字段 | 类型 | 说明 |
|---|---|---|
| flowId | string | 回显 |
| notebookId | string | 挂在哪个多维表下 |
| tableId | string \| null | 触发表。`null` = 还没设置，这条流不会被触发。重复登记时是**已登记的现状**，不是本次传的值 |
| createdTime | string | 关联建立时间（ISO 8601） |
| lastModifiedTime | string \| null | 最后修改时间；从未改过为 `null` |
| alreadyRegistered | `true` | **仅当**这个 `flowId` 之前就登记过时出现，表示本次是幂等返回现状、没有新建 |

### 语义与坑
- **只登记关联，不创建工作流**：存的是 `notebookId` + `flowId` + 可选触发表；流的定义、节点、启停都在工作流侧。顺序固定为「先在工作流侧建流 → 再调本操作登记」。
- 登记之后两件事会发生：① 这条流出现在多维表的侧栏节点树里；② 指定了触发表的话，那张表的记录变化会被推送出去驱动这条流。
- **重复登记是安全的**：同一个 `flowId` 再调一次不会建出第二条，直接回现状并带 `alreadyRegistered: true`。所以「建流成功但登记这一步超时 / 断网」可以直接重试。
- ⚠️ **但重试不会改 `tableId`**：已登记的流即使这次传了不同的 `tableId` 也不会被改掉——改触发表是 `updateWorkflowTriggerTable` 的语义。让重试顺手改配置等于给「重试」加副作用：网络抖动重发一次就把用户配好的触发表换掉了，而且没有任何提示。看到 `alreadyRegistered: true` 而你确实想换表，就再调 `updateWorkflowTriggerTable`。脚本在这种情况下会在 stdout 打出同样的提醒。
- **`tableId` 留空是正常状态**：触发表通常是用户在工作流画布的触发器节点里选的，登记那一刻往往还没配。留空的流照样出现在侧栏（用户要能点进去补配置），但**不会被任何记录变化触发**，之后用 `updateWorkflowTriggerTable` 补上。成功但 `tableId` 为 `null` 时脚本会在 stdout 提醒这一点。
- ⚠️ **`tableId` 必须是 `notebookId` 这个多维表里面的表**，否则 400（权限校验，理由见上文「四个操作都适用的规则」）。
- **`notebookId` 别拿 `tableId` 顶替**：两个列表接口出参是两层的，顶层 `notebooks[].notebookId` 才是这里要的，里面 `tables[].tableId` 是数据表。传 `tbl` 开头的值脚本会在本地拦下；服务端对传错的 id 只会回一个 404。
- **只能登记到自己团队、且自己有写权限的多维表下**（拥有者 / 创建者 / 可编辑者）。只读成员登记不了，拿到的是 404 而不是 403。
- **`flowId` 传错不会当场报错**，只会登记出一条指向不存在的流的关联——这个 id 要从工作流侧拿。
- **汇报**：成功后说明登记到了哪个多维表、触发表是哪张（或「还没设置触发表」）；`alreadyRegistered: true` 时**如实说「本来就已经登记过」**，别说成「登记成功」——用户可能以为自己刚才那次操作没生效；`tableId` 为 `null` 时主动提醒这条流现在**不会被任何记录变化触发**、需要设置触发表；报错时把 `errmsg` 原文转述。

### 常见错误
| errmsg 关键词 | 原因 | 怎么办 |
|---|---|---|
| 本地：`缺少 notebookId（多维表 id，以 nbk 开头）` | 没传 `notebookId` | 补上，取自列表接口顶层 |
| 本地：`notebookId 传的是数据表 id（tbl 开头）` | 把 `tableId` 当 `notebookId` 传了 | 改取 `notebooks[].notebookId`，不是 `tables[].tableId` |
| 本地：`缺少 flowId（工作流侧那条流的 id）` | 没传 `flowId` | 从工作流侧拿，不要自己编 |
| 本地：`tableId 必须是以 tbl 开头的字符串，或 null` | `tableId` 形态不对 | 传 `tbl` 开头的 id；还没定就不传或传 `null` |
| 400（入参不合法，或 `tableId` 不在这个多维表下面） | 参数不对，或跨多维表绑定 | 按 `errmsg` 改。跨多维表绑定是被禁止的，换一张该多维表里的表 |
| 404 `Notebook ... not found` | **三种成因合成一种**：id 写错 / 不在你团队 / 你对它没有写权限。看不见的资源连是否存在都不透露，否则可以拿这个接口去探测别的团队有哪些多维表 | 自己核对两件事：① `notebookId` 是不是取自列表接口**顶层** `notebooks[].notebookId`（不是 `tableId`）；② 当前身份对该多维表是不是拥有者 / 创建者 / 可编辑者之一（只读成员登记不了）。脚本会在 stderr 附同样的提示 |
| 500 / 503 | 服务端异常 / 数据库暂不可用 | 稍后重试，**幂等所以安全** |

### 示例
**1. 登记时还没选触发表（最常见）**
```json
{"notebookId": "nbkXXXXXXXX", "flowId": "your-flow-id"}
```

**2. 登记时就指定触发表**
```json
{"notebookId": "nbkXXXXXXXX", "flowId": "your-flow-id", "tableId": "tblXXXXXXXX"}
```

## listWorkflows —— 列出哪条流挂在哪个多维表下、由哪张数据表触发（只读）

**何时用 / 不该用**：
- 用：想知道某个多维表下挂了哪些自动化；排查「自动化没触发」时先确认它绑的是哪张表、有没有绑；`updateWorkflowTriggerTable` / `unregisterWorkflow` 之前确认 `flowId`。
- 不该用：要**登记**新关联 → `registerWorkflow`；要**改触发表** → `updateWorkflowTriggerTable`；要**解除**关联 → `unregisterWorkflow`；要流的**名字 / 详情 / 运行记录** → 本操作给不了，到工作流侧按 `flowId` 查；要看表里的**数据** → `listRecords`（见 `references/records-read.md`）；要看有哪些**表** → `listMyTables` / `listSharedTables`（见 `references/tables.md`）。

**调用**：`python scripts/smart_table.py listWorkflows '{}'`（列全部）或 `'{"notebookId":"nbkXXXXXXXX"}'`。参数整个省略等价于 `{}`。

### 参数
| 参数 | 类型 | 必填 | 默认 | 约束 | 说明 |
|---|---|---|---|---|---|
| notebookId | string | 否 | 不传 | `nbk` 开头的非空字符串，或整个省略 | 只看这个多维表下的关联。不传 = 当前团队里自己能看到的全部 |

没有分页参数（没有 `page` / `perPage`），也不收 `baseId`。

### 响应
| 字段 | 类型 | 说明 |
|---|---|---|
| total | integer | 条数。不分页，所以必然等于 `workflows` 数组长度 |
| workflows | array[object] | 关联列表，**按创建时间倒序**（不可参数化） |
| workflows[].flowId | string | 工作流侧那条流的 id |
| workflows[].notebookId | string | 挂在哪个多维表下 |
| workflows[].tableId | string \| null | 触发表。**`null` = 没设置，这条流不会被任何记录变化触发** |
| workflows[].createdTime | string | 关联建立时间（ISO 8601） |
| workflows[].lastModifiedTime | string \| null | 最后修改时间；从未改过为 `null` |

### 语义与坑
- **只读**，不改任何东西。
- **不分页**：一个团队的流是十几条的量级，一次全给。
- **按可见性过滤**，与多维表侧栏、节点树同一份口径——你看不见的多维表下面的流不会出现在结果里。所以**「列表里没有」不等于「不存在」**，也可能是没权限看那个容器。给了 `notebookId` 但你看不见那个容器时，同样回空列表（不是 403）——看不见的东西连它存在都不该告诉你。只能看到**自己团队**、且**自己可见**的多维表下的关联。
- **空列表是成功不是报错**：团队还没建过任何东西时回 `{"total": 0, "workflows": []}`，「还没建过任何东西」是正常状态，别把空列表当失败。但空结果的成因有两种——确实没有登记过任何工作流关联，或者那些多维表当前身份看不见；脚本会在 stdout 提醒这两种可能，别只报「没有自动化」。
- **`tableId` 为 `null` 的流不会被触发**，是排查「自动化怎么不跑」最该先看的一项：这类流照样在列表里、照样在侧栏可见，看着很正常，但记录变化推不到它。两种成因：① 登记时还没选触发表（触发器在工作流画布里配，登记那一刻常常还没配完）；② 原触发表被删除或被移出多维表，后端**自动**把它置空了。脚本会在 stdout 列出这类 `flowId`（最多 10 个）。
- ⚠️ **`notebookId` 别拿 `tableId` 顶替**：传一个 `tbl` 开头的 id，服务端回的是**空列表而不是报错**，很容易被误读成「这个多维表下没有自动化」。脚本在本地就拦下这种入参。
- 不返回流的名字、启停状态、触发条件——那些都在工作流侧（见上文「四个操作都适用的规则」）。
- **汇报**：按多维表分组，每条给出 `flowId` + 触发表；**`tableId` 为 `null` 时明确标注「未设置触发表，不会被触发」**——这是用户最关心的异常态；只有 id 没有名字时，说明「流的名字要到工作流侧按 flowId 查」，不要编名字；空结果要区分上面两种可能。

### 常见错误
| errmsg 关键词 | 原因 | 怎么办 |
|---|---|---|
| 本地：`notebookId 传的是数据表 id（tbl 开头）` | 把 `tableId` 当 `notebookId` 传了（服务端只会回空列表，所以本地拦下） | 改取列表接口顶层 `notebooks[].notebookId` |
| 本地：`notebookId 必须是非空字符串（多维表 id，以 nbk 开头），或整个省略` | 传了空串 / 非字符串 | 传正确的 `nbk` id，或不传 |
| 400 入参不合法 | 参数不对 | 按 `errmsg` 改 |
| 500 / 503 | 服务端异常 / 数据库暂不可用 | 只读接口，稍后重试即可，安全 |

### 示例
**1. 列出全部**
```json
{}
```

**2. 只看某个多维表下的**
```json
{"notebookId": "nbkXXXXXXXX"}
```

## updateWorkflowTriggerTable —— 改（或清空）一条已登记流的触发数据表

**何时用 / 不该用**：
- 用：用户要把自动化改成监听另一张数据表；原触发表被删后重新挑一张；要停掉某条自动化的触发（传 `null` 解绑，关联还在、侧栏还看得到、以后好恢复）。
- 不该用：原表刚被删、只想让它「自动失效」→ **不用调**，后端已自动置空；要**登记**新关联 → `registerWorkflow`；要**解除**整条关联（不只是触发表）→ `unregisterWorkflow`；要**看**当前绑的是哪张表 → `listWorkflows`；要改流的名字 / 节点 / 启停 → 做不到，到工作流侧改；要改表里的**数据** → `updateRecords`（见 `references/records-write.md`）。

**调用**：`python scripts/smart_table.py updateWorkflowTriggerTable '{"flowId":"your-flow-id","tableId":"tblYYYYYYYY"}'`

### 参数
| 参数 | 类型 | 必填 | 默认 | 约束 | 说明 |
|---|---|---|---|---|---|
| flowId | string | **是** | — | 非空字符串，**不校验格式** | 工作流侧那条流的 id（可用 `listWorkflows` 查）。抄错只会得到 `not_found` |
| tableId | string \| null | **是（可为 `null`）** | 无默认，必须显式给 | `tbl` 开头，或 `null`；**必须与该流同属一个多维表** | 新的触发表。**`null` = 解绑**，这条流退回「没有触发表」、不再被触发 |

| 传什么 | 含义 |
|---|---|
| `"tblXXXXXXXX"` | 换成这张表触发 |
| `null` | **解绑**——不再被任何记录变化触发 |
| 不传这个字段 | ❌ 本地预检直接报错。**不能**用「省略」来表达解绑 |

### 响应
| 字段 | 类型 | 说明 |
|---|---|---|
| status | `"updated"` \| `"not_found"` | `updated` = 改了；`not_found` = 我们这边没有这个 `flowId` 的关联，**什么都没改** |
| flowId | string | 仅 `updated` 时有 |
| notebookId | string | 仅 `updated` 时有。这条流所属多维表（本操作不会改它） |
| tableId | string \| null | 仅 `updated` 时有。改完之后的触发表；`null` = 已解绑 |
| createdTime | string | 仅 `updated` 时有。关联建立时间（ISO 8601） |
| lastModifiedTime | string \| null | 仅 `updated` 时有 |

找不到时整条响应就是（**注意 errcode 仍是 200**）：`{"errcode": 200, "errmsg": "ok", "status": "not_found"}`

### 语义与坑
- ⚠️ **errcode 200 不代表改动生效，必须看 `status`**。**把 `not_found` 当成成功汇报给用户是这条接口最容易犯的错**——它表示什么都没改。脚本遇到 `not_found` 会在 stderr 打警告。
- 只改触发层：不碰流本身（名字、节点、启停都在工作流侧），也不碰归属（这条流仍然挂在原来那个多维表下）。
- **`tableId` 必填但可为 `null`——为什么不做成可选**：「解绑」和「这次不改」必须由调用方明确区分开。做成可选的话，少传一个字段就会被当成解绑，于是一次手滑就**静默停掉一条自动化**：用户以为流还在跑，实际早已不触发，而且没有任何报错。所以契约上它是 `nullable` 而不是 `optional`：**要解绑就显式传 `null`**。脚本用「键在不在」而不是「值是不是 null」来判断，漏传键在本地就报错。
- **两种失败形态，刻意不合并**：

  | 情况 | 返回 | 为什么这样设计 |
  |---|---|---|
  | 查不到这条关联（含 `flowId` 属于别的团队） | 200 + `status: "not_found"` | 幂等。重试、或那条流本来就没在多维表里登记过，都不算错误；报错会让调用方的流程卡在无法自愈的状态上。跨团队也按「我这边没有」回，不透露它存在于别处 |
  | **权限不足 / 新表不在那个多维表下** | **403 / 400（真的失败）** | **不伪装成 `not_found`**。否则「你配不上这张表」变成静默的：调用方以为登记没生效、一直重试，用户永远配不上而且没有任何提示 |

  所以：`not_found` → 先怀疑 `flowId` 抄错或还没登记；`403` → 如实告诉用户是**权限问题**。
- ⚠️ **新表必须与该流同属一个多维表**：这条流挂在哪个多维表下，触发表就只能选那个多维表里的表，否则 400（权限校验，理由见上文「四个操作都适用的规则」）。
- **要换的表 id 从哪来**：先用 `listWorkflows` 查到这条流挂在哪个 `notebookId` 下，再用 `listMyTables`（见 `references/tables.md`）找那个多维表里的 `tables[].tableId`。别从别处拿一个 `tableId` 直接试。
- **原触发表被删除时不需要调这条**：后端已经自动置空了（删表、删节点、把表移出多维表三个入口都挂了自动清理），那条流会自己退回「没有触发表」。本操作是给**用户主动换表**用的（换一张、或原表被删后重新挑一张）。自动置空通知不到工作流侧这个缺口见上文「两层关联」。
- ⚠️ **解绑要先向用户确认**：传 `null` 会让一条自动化不再触发——虽然可逆（再设回去就行），但用户往往不知道「解绑」等于「停掉」。先说清楚再做。脚本对本操作**没有** `--yes` 闸门，这一步只能靠调用方自己守。解绑成功后脚本会在 stdout 提醒「没有触发表、不会再被触发；要恢复再调一次传上新的 tableId」。
- 只能改**自己团队**、且**自己有写权限**的多维表下的流（拥有者 / 创建者 / 可编辑者）。一条流只能绑**一张**触发表。
- **汇报**：`updated` → 说明这条流现在由哪张表触发；解绑的话明确说「**不再被任何记录变化触发**」。`not_found` → **不要说成成功**，如实说「多维表这边没有这条流的关联」，并提示先用 `listWorkflows` 确认 `flowId`，或先用 `registerWorkflow` 登记。403 → 如实说是**权限不足**（对那个多维表没有写权限），不要说成「找不到」。400 → 大概率是新表不在这条流所属的多维表下面，把这一点说清楚。

### 常见错误
| errmsg 关键词 | 原因 | 怎么办 |
|---|---|---|
| 本地：`缺少 flowId（工作流侧那条流的 id）` | 没传 `flowId` | 用 `listWorkflows` 查 |
| 本地：`缺少 tableId。这个参数**必填**` | 没传 `tableId` 这个键 | 要换表传 `tbl` 开头的 id；要解绑**显式传 `null`** |
| 本地：`tableId 必须是以 tbl 开头的字符串，或 null（解绑）` | `tableId` 形态不对 | 同上 |
| errcode 200 + `status: "not_found"` | 多维表这边没有这个 `flowId` 的关联：`flowId` 抄错、还没登记、或属于别的团队。**什么都没改** | 用 `listWorkflows` 核对 `flowId`，或先 `registerWorkflow` 登记。不要汇报成「修改成功」 |
| 400（入参不合法，或新表不在这条流所属的多维表下面） | 多半是跨多维表绑定 | 触发表只能选该流所属多维表里的表，按上面「要换的表 id 从哪来」重新取 |
| 403 无权改这条流 | 对那个多维表没有写权限（需拥有者 / 创建者 / 可编辑者） | **如实告诉用户是权限问题**，不要说成「找不到」。脚本会在 stderr 附同样的提示 |
| 500 / 503 | 服务端异常 / 数据库暂不可用 | **先用 `listWorkflows` 确认实际状态**，再决定是否重试 |

### 示例
**1. 换成另一张表触发**
```json
{"flowId": "your-flow-id", "tableId": "tblYYYYYYYY"}
```

**2. 解绑（这条流不再被触发，先向用户确认）**
```json
{"flowId": "your-flow-id", "tableId": null}
```

## unregisterWorkflow —— 把一条流从多维表下面摘掉（不删除工作流本身）

**何时用 / 不该用**：
- 用：要彻底删掉一条流时的**第 1 步**（先解除关联、再到工作流侧删流）；工作流侧已经删了一条流，要清掉多维表这边的关联；用户要把某条自动化从多维表下面摘掉。
- 不该用：只想让自动化**暂时不触发** → `updateWorkflowTriggerTable` 传 `tableId: null`；要**删除工作流本身** → 本操作不做，到工作流侧删（先调本操作解除关联）；要**改触发表** → `updateWorkflowTriggerTable`；要**登记**关联 → `registerWorkflow`；要**看**有哪些关联 → `listWorkflows`；要删表里的**记录** → `deleteRecords`（见 `references/records-write.md`）。

**调用**：`python scripts/smart_table.py unregisterWorkflow '{"flowId":"your-flow-id"}' --yes`（**必须带 `--yes`**）

### 参数
| 参数 | 类型 | 必填 | 默认 | 约束 | 说明 |
|---|---|---|---|---|---|
| flowId | string | **是** | — | 非空字符串，**不校验格式** | 工作流侧那条流的 id（可用 `listWorkflows` 查）。抄错只会得到 `not_found` |

⚠️ **不收我们内部的关联行 id**（`wfl...` 那种）——那个 id 调用方手上没有，所以按 `flowId` 寻址。也不收 `baseId`。

### 响应
| 字段 | 类型 | 说明 |
|---|---|---|
| status | `"unregistered"` \| `"not_found"` | `unregistered` = 本次真的解除了；`not_found` = 我们这边本来就没有这条关联。**两者都是成功**，都表示「多维表这边已经没有这条流了」 |

除 `errcode` / `errmsg` 外没有别的字段。

### 语义与坑
- **做什么**：删掉「这条流属于这个多维表」这条关联记录。之后它从多维表侧栏消失，原触发表的记录变化也不再推送给它。**不做**：**不删除工作流**——流的定义、节点、历史运行记录都还在工作流侧，只是不再和这个多维表有关系。
- ⚠️ **`--yes` 闸门**：不带 `--yes` 脚本拒绝执行、不发请求，stderr 说明后果并 **exit 2**（参数本身不合法时先报参数错、exit 1）。正确做法：先用 `listWorkflows` 读出来给用户看，确认要摘哪一条，再加 `--yes` 重跑。虽然不删流，但这条流会从多维表消失、不再被触发，所以**要向用户确认**。
- **不可逆，但可重新登记**：解除之后关联记录就没了；要恢复得用 `registerWorkflow` 重新登记（**触发表也要重新设**）。**不进前端撤销栈**，用户在页面上撤不回来。
- **幂等：两种 `status` 都是成功**。`not_found` 的成因是重试、或那条流压根没在多维表里登记过——都不是错误。报错会让调用方的删除流程卡在一个**无法自愈**的状态上：流已经删了、关联清不掉、每次重试都报错。所以**收到 200 就可以认为已经清干净了，不必区分两种 status，也不要重试**。
- ⚠️ 唯一要留个心的是：**`flowId` 抄错也会得到 `not_found`**。如果你确信这条关联应该存在，先用 `listWorkflows` 核对 id，别直接当成「已经清干净了」。
- ⚠️ **顺序：先解除关联，再删流**，不能反过来：
  ```
  ① 解除关联 ──► unregisterWorkflow
  ② 删流     ──► 工作流侧
  ```
  先删流再解除的话，第 2 步失败会在多维表侧栏留一个**点不开的死节点**（节点树是侧栏的唯一数据源），用户看得见就是 bug 报告。先解除再删流，第 2 步失败只是流留在工作流侧、多维表里看不见——用户看不到的不算问题。另有一个懒清理兜底：前端按 id 查流详情时拿到 404 就顺手解除；但没人打开那张多维表就一直不清理，**不能依赖它**。
- **为什么这条通知不能漏**：外推闸门是「这张表上有流才发消息」。**一条已删的流会让那张数据表永久保持发消息状态**——每次记录变化都推一条没人消费的消息出去。所以工作流侧删流时必须调这条。
- **判权与其余操作不同（刻意的）**：本操作**不判容器写权限**，而 `registerWorkflow` / `updateWorkflowTriggerTable` 判。这里的授权依据不是「这个人能不能改那个多维表」，而是「工作流侧说这条流已经没了」，可信性来自网关签发的身份令牌。要是走容器写权限，网关注入的那个成员一旦对该多维表没有写权，这条通知就会**恒 404 失败**——而它是清理通知，失败就意味着永久留一条死关联。
- **团队边界仍然守着**：`flowId` 全局唯一，服务端会校验它属于调用方所在团队——不属于就按 `not_found` 回（**不告诉你它存在于别的团队**）。所以拿不到别人团队的东西；正常场景碰不到这条。
- **别用它来「停掉」一条自动化**：只是想让它暂时不触发，用 `updateWorkflowTriggerTable` 传 `null` 解绑触发表就够了——关联还在、侧栏还看得到、以后好恢复。
- **汇报**：成功后说明这条流已从多维表移除、不再被触发，并明确说**流本身还在工作流侧**（用户很容易以为流也被删了）；`not_found` 时如实说「多维表这边本来就没有这条关联」，并提示确认 `flowId`——不要含糊地说成「已解除」；用户本意是「彻底删掉这条流」的，提醒他们还要到工作流侧做第 2 步。

### 常见错误
| errmsg 关键词 | 原因 | 怎么办 |
|---|---|---|
| 本地：`拒绝执行：解除关联不可逆`（exit 2） | 没带 `--yes` | 先 `listWorkflows` 给用户确认是哪一条，再加 `--yes` 重跑；只想暂停就改用 `updateWorkflowTriggerTable` 传 `null` |
| 本地：`缺少 flowId（工作流侧那条流的 id）` | 没传 `flowId` | 用 `listWorkflows` 查 |
| errcode 200 + `status: "not_found"` | 本来就没有这条关联：重试过、没登记过、`flowId` 抄错、或属于别的团队 | 目标已达成，**不要重试**；确信它应该存在时用 `listWorkflows` 核对 id |
| 400 入参不合法（`flowId` 为空等） | 参数不对 | 按 `errmsg` 改 |
| 500 / 503 | 服务端异常 / 数据库暂不可用 | 可以重试，**幂等所以安全** |

**没有 403 / 404**——查不到、跨团队都归到 200 + `status: "not_found"`。

### 示例
```json
{"flowId": "your-flow-id"}
```

命令：`python scripts/smart_table.py unregisterWorkflow '{"flowId":"your-flow-id"}' --yes`
